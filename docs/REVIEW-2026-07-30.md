### Amended note on SEC-01

The operator has decided to run the system over plain HTTP. That decision is recorded here
so the finding is not repeatedly re-raised. What changed in code:

- login throttling now exists (10 failed attempts per identifier, 50 per IP, 15-minute
  rolling window, hashed identifiers and IPs, generic message and HTTP 429 so account
  enumeration stays impossible);
- `SESSION_HTTPS_ONLY` is no longer hard-coded — a `tls_enabled` profile flag drives it and
  the `PUBLIC_BASE_URL` scheme, defaulting to `False` so existing HTTP behaviour is
  unchanged;
- a public listener can no longer be staged with an empty permitted-remote-networks list,
  which previously produced a firewall rule open to the entire internet.

The residual risk is unchanged and unmitigated: on-path observers can read session cookies
and passwords in transit. The strongest available compensating control is a narrow
`allowed_remote_ips` list or a VPN, which the validation change now forces the operator to
consider.

### Outstanding operational step

The code side of BAK-01/BAK-02 is complete, but **no restore has been rehearsed**. A backup
system is only proven by a restore. Until a scheduled dump and its same-timestamp
`uploads-` snapshot have been restored into a scratch environment and every photo confirmed
to resolve, this is a backup system that *should* work rather than one known to work. The
procedure is in `docs/PRODUCTION_UPDATES.md`.

### Minor items noted during remediation, not yet actioned

- `Remove-OldBackupItems` and the `$previousSnapshot` selection in the generated backup
  runner sort by `LastWriteTimeUtc`. Snapshot names (`uploads-<yyyyMMdd-HHmmss>`) sort
  lexicographically in chronological order, so sorting by `Name` would be more robust
  against a perturbed directory mtime. Pre-existing style, not a regression.
- The review originally said unbounded PDF generation "blocks the only worker". FastAPI runs
  sync `def` endpoints in a threadpool, so it occupies one thread rather than the process.
  The memory, database and image-processing exhaustion was real and the fix stands.

## 1. Executive summary

**Overall condition.** This is a well-built, disciplined application. The architecture
matches its documentation, authorization is genuinely enforced in FastAPI dependencies
(all 94 protected routes were verified empirically across five identities, not by
reading templates), Customer Project isolation holds under direct IDOR probing, CSRF is
enforced on every state-changing POST, and the upload pipeline is properly defended. The
snapshot-based history model is applied consistently across all three record types. Code
quality is high and the test suite is real.

The problems are concentrated **outside** the request/response layer: in deployment
posture, concurrency, backup/DR, and unbounded work. The single most important
qualitative finding is that the intended production deployment path — public HTTP, no
TLS, no login throttle — is the weakest part of an otherwise solid system.

**Production-readiness verdict at review time: Ready only after listed blockers.** See
section 9 — that verdict has since been superseded; the current position is in section 9.1.

**Findings: 1 Critical · 5 High · 10 Medium · 9 Low · 6 Informational (31 total).**
*Since remediation: 18 closed, 2 partly closed, 8 open (all Medium or below) — section 0.*

### Five most urgent risks

1. **SEC-01** — The documented production path transmits Administrator credentials and
   session cookies in cleartext over a public IP, with no rate limiting and
   `SESSION_HTTPS_ONLY` hard-coded to `false` by the apply script.
2. **REL-01** — Record-number allocation has a confirmed lost-update race. Two concurrent
   submissions receive the same record number; the second commit fails and **its
   already-uploaded photos are deleted**. Reproduced during this review.
3. **BAK-01** — The only automated backup is database-only. The photo evidence — the
   entire point of the product — has no scheduled backup.
4. **BAK-02** — Backup failure is silent. The Settings page shows the last status file
   forever; a task that stops running never surfaces.
5. **TEST-01** — Alembic migrations are never executed by any test. The suite builds its
   schema with `create_all()`, so schema/model drift is undetectable, yet
   `alembic upgrade head` runs against production on every deploy.

### Strong controls already implemented (verified, not assumed)

- Authorization in dependencies, not templates — the full 94-route x 5-role matrix
  matches the documented intent exactly (section 4).
- Customer Project isolation confirmed by direct probe: cross-project record → 403,
  cross-project photo → 403, edit → 403.
- Three-gate upload validation (extension → magic bytes → Pillow decode with format
  cross-check), UUID storage keys outside the static root, regex-validated storage keys
  with a resolved-path containment check.
- CSRF enforced on every state-changing POST, backed by `SameSite=Lax` — defence in depth.
- Zero `|safe`, zero `Markup`, zero `autoescape false` in templates; `tojson` used
  correctly for the one embedded JSON block; all dynamic JS uses `textContent`.
- No SQL injection anywhere — every query is SQLAlchemy expression-language; every
  user-supplied ID passes `.isdigit()` before `int()`.
- `_safe_next` open-redirect probing failed on all vectors (`//`, `https://`, `/\`) —
  Starlette percent-encodes the backslash, so `/%5Cevil` stays same-origin.
- Server-clock timestamps, single-use form tokens, session invalidation via
  `auth_version`, hashed/expiring/single-use recovery tokens with per-account and per-IP
  throttling.
- Decimal money throughout with explicit `ROUND_HALF_UP` quantisation; snapshot-based
  quotations.

## 3. Detailed findings

### SEC-01 — Production deployment path transmits credentials and sessions in cleartext, with no login throttle

**Severity:** Critical (conditional — see Likelihood)
**Confidence:** Confirmed
**Category:** Security / deployment

**Affected files**

- `app/deployment_config.py:322` — `Set-EnvValue $envPath 'SESSION_HTTPS_ONLY' 'false'`
- `app/deployment_config.py:323` — `$baseUrl = ... "http://${publicIp}:${publicPort}"`
- `app/main.py:46-53` — session cookie, `https_only=settings.session_https_only`
- `app/routers/auth.py:71-118` — `login_submit`, no throttle
- `app/main.py:72-78` — no HSTS (correctly, since there is no TLS)
- `README.md:190-231`, `app/templates/settings.html:18`

**Evidence.** The generated apply script writes `SESSION_HTTPS_ONLY=false` into `.env`
unconditionally and sets `PUBLIC_BASE_URL` to an `http://` origin. The session cookie
therefore carries no `Secure` flag. `app/routers/auth.py` has no lockout, no delay, no
attempt counter — the recovery flow has throttling (`account_recovery.py:125-157`,
5/identifier and 20/IP per 15 min) but login has none. `README.md:314` acknowledges this:
*"No rate limiting on login. There is no lockout or throttle after repeated failures."*

**Why it matters.** The session cookie is the complete authentication credential. On-path
capture of one Administrator cookie grants full access to every record, every photo, user
management, and Deployment Settings. Separately, unlimited password guessing against a
known-format username (the account is literally named `admin`) with no lockout is a
standard path to compromise.

**Likelihood.** High *if* public HTTP is enabled on a real public IP without a VPN or a
narrow `allowed_remote_ips` list. Low if the deployment stays LAN-only or behind a VPN.
The product ships an entire Settings module to enable exactly this, so the exposed
configuration is treated as a realistic operating state. The Settings page does display a
warning banner (`settings.html:18`) — good, but a banner is not a control.

**Realistic scenario.** Public listener enabled with `allowed_remote_ips` left blank (the
firewall rule then uses `-RemoteAddress Any`, per `deployment_config.py:297`).
Internet-wide scanning finds `:8993`. An attacker runs unthrottled credential guessing;
separately, any technician using the portal from hotel or site Wi-Fi has their session
cookie captured verbatim.

**Affected users/data.** All users; all records, photos, customer contact details, and
pricing.

**Remediation.**
(a) Terminate TLS in front of the app — IIS/ARR reverse proxy or a Windows-hosted reverse
proxy with an ACME certificate — and set `SESSION_HTTPS_ONLY=true`; the apply script
should set it from a new "TLS enabled" setting rather than hard-coding `false`.
(b) Add login throttling: `slowapi`, or a small `login_attempts` table mirroring
`AccountRecoveryAttempt`, which already gives you a tested pattern.
(c) Make `allowed_remote_ips` mandatory when `public_enabled` is true, or refuse to
generate a public rule with `-RemoteAddress Any`.

**Effort:** Medium.
**Migration/ops:** Ops change (certificate, proxy); one small migration if you add a
`login_attempts` table.

**Verification test.** Assert the generated apply script never emits
`SESSION_HTTPS_ONLY 'false'` when TLS is on; assert the 6th failed login within N seconds
returns 429; assert `validate_profile` rejects `public_enabled` with empty
`allowed_remote_ips`.

### REL-01 — Record-number allocation race loses submissions and deletes already-uploaded evidence

**Severity:** High
**Confidence:** Confirmed (reproduced)
**Category:** Data integrity / concurrency

**Affected files**

- `app/helpers.py:33` — `db.get(RecordCounter, year, with_for_update=False)`
- `app/helpers.py:51` — same for `InstallationRecordCounter`
- `app/helpers.py:68` — same for `GeneralMaintenanceRecordCounter`
- `app/pricing.py:78-82` — same for `PricingQuotationCounter`
- Failure paths: `maintenance.py:526-557`, `installations.py:575-606`,
  `general_maintenance.py:428-451`

**Evidence.** Both variants were reproduced against the isolated test database.

*Existing counter row (`last_sequence=5`), two concurrent allocations:*

```
B still blocked while A uncommitted: True
allocated numbers: {'a': 'PM-2026-00006', 'b': 'PM-2026-00006'}
counter now: 6
```

Both sessions receive `PM-2026-00006`. The row lock serialises the `UPDATE`, but because
SQLAlchemy emits `SET last_sequence = 6` (a literal computed from a stale read) rather
than `SET last_sequence = last_sequence + 1`, B's write is a classic lost update.
`with_for_update=False` is explicit in the code, so no `SELECT ... FOR UPDATE` re-read
occurs.

*First record of a new year, counter row absent:*

```
session A allocated: PM-2026-00001
B blocked while A open: True
session B: IntegrityError('duplicate key value violates unique constraint "record_counters_pkey"')
```

**Why it matters.** `maintenance_records.record_number` is `UNIQUE`, so the database
correctly refuses the duplicate — integrity is preserved. But the second technician's
`db.commit()` raises, the handler rolls back, **calls `delete_stored(...)` on every photo
it just wrote**, and returns *"The record could not be saved. Try again."* Because
browsers cannot repopulate a file input (`README.md:313`), the technician must reselect or
re-shoot every photo. On a mobile connection over which they just uploaded 20 MB, that is
a serious field failure.

**Likelihood.** Medium-high. A crew finishing a site together, or one technician filing a
backlog while a colleague files theirs, collides easily. Every 1 January, the first two
submissions of the year collide on the `record_counters_pkey` variant.

**Affected users/data.** All record submitters; all four counter-backed number series
(`PM-`, `NI-`, `MA-`, quotations).

**Remediation.** Change all four call sites to `with_for_update=True`, which makes
PostgreSQL re-read the row after acquiring the lock. Handle the missing-row case with
`INSERT ... ON CONFLICT (year) DO NOTHING` followed by a locked re-select, or catch
`IntegrityError` and retry once.

**Effort:** Small.
**Migration/ops:** None.

**Verification test.** Two threads on two sessions allocating from the same counter must
return distinct numbers, and the counter must equal the highest allocated value. Repeat
with no pre-existing counter row.

### BAK-01 — Scheduled backup protects the database only; photo evidence has no automated backup

**Severity:** High
**Confidence:** Confirmed
**Category:** Backup / DR

**Affected files**

- `app/deployment_config.py:508-629` — `database_backup_windows_script`, `pg_dump` only
- `app/models.py:1204-1222` — backup settings model has no upload-directory field
- `scripts/Deploy-Release.ps1:159-163` — uploads copied only at release time
- `CLAUDE.md` — *"This schedule is database-only and does not back up uploaded photos"*
- `README.md:222` — same

**Evidence.** The generated `Backup-Database.ps1` runner invokes `pg_dump` and prunes
`service-management-*.dump`. There is no upload-directory handling anywhere in the
scheduled path. Uploads are copied only by `Deploy-Release.ps1`, i.e. only when a new
version is deployed.

**Why it matters.** The product's stated purpose is a *maintenance evidence portal*. The
database holds `storage_key` pointers; the actual proof lives on disk. A restore from a
scheduled dump reproduces every record with every photo missing — the
`/media/photo/{id}` route resolves the key, `resolve_storage_path` raises `UploadError`,
and the user gets 404 for every image. The evidence trail is gone while appearing
structurally intact.

**Likelihood.** Certain in any disk-loss or ransomware scenario between deployments. If
releases are quarterly, the upload RPO is up to three months.

**Affected users/data.** All photo evidence for all Projects.

**Remediation.** Extend the scheduled task to snapshot `UPLOAD_DIR` alongside each dump
(robocopy mirror to a dated folder, or a compressed archive), with independent retention.
Because photos are immutable once written, an incremental/mirror copy is cheap. The dump
and the upload snapshot must be taken in that order and labelled with the same timestamp
so a restore pair is unambiguous.

**Effort:** Medium.
**Migration/ops:** Migration (new `backup_uploads_directory` / `backup_include_uploads`
columns) plus regenerating and re-running the installer script.

**Verification test.** Restore a dump plus its paired upload snapshot into a scratch
environment and assert every `maintenance_photos.storage_key` resolves to an existing
file.

### BAK-02 — Backup failure is silent; no staleness detection, no alerting, no restore verification

**Severity:** High
**Confidence:** Confirmed
**Category:** Backup / DR

**Affected files**

- `app/routers/settings.py:71-84` — `_backup_status()` reads the JSON status file and
  returns it as-is
- `app/templates/settings.html:193-196` — renders `backup_status.ok` and `completed_utc`
  verbatim
- `app/deployment_config.py:572-586` — the runner writes status then re-raises

**Evidence.** `settings.html:194` renders
`<div class="alert {{ 'success' if backup_status.ok else 'error' }}">`. Nothing compares
`completed_utc` against `backup_interval_days`. If the scheduled task is deleted,
disabled, fails to start, or the server is powered off at 02:00, the last successful
status stays on screen showing a green *"Database backup completed."* indefinitely.

**Why it matters.** This is the failure mode that turns a recoverable incident into an
unrecoverable one: the operator has an affirmative, and false, signal that backups are
healthy. There is also no automated restore verification anywhere —
`docs/PRODUCTION_UPDATES.md:117-136` documents restore as a manual, deliberately
non-automatic procedure, which is a reasonable safety choice, but nothing ever proves a
dump is restorable.

**Likelihood.** High over any multi-month operating period.

**Affected users/data.** All data; the organisation's ability to recover at all.

**Remediation.**
(a) In `_backup_status()`, compute age from `completed_utc` and mark the status
stale/error when it exceeds `backup_interval_days` x 24 h plus a grace window — treat a
missing status file as an error, not as "no information".
(b) Have the runner also record `last_success_utc` separately from `last_attempt_utc`.
(c) Add a documented quarterly restore drill to `PRODUCTION_UPDATES.md`, ideally scripted
against a scratch database with a row-count and photo-resolution assertion.

**Effort:** Small for (a)+(b); Medium for (c).
**Migration/ops:** Ops change; regenerate the installer script.

**Verification test.** Write a status file with `completed_utc` three intervals old and
assert the Settings page renders an error state.

### PERF-01 — Unbounded report and PDF generation on a single synchronous worker

**Severity:** High
**Confidence:** Confirmed
**Category:** Performance / availability

**Affected files**

- `app/record_views.py:147-496` — `load_record_views` loads **all** matching records into
  Python, sorts in memory
- `app/routers/records.py:32-41` and `app/routers/reports.py:44-53` — load everything,
  then slice for pagination
- `app/routers/reports.py:67-102` — `/reports/pdf` calls with `include_evidence=True` and
  no limit
- `app/report_pdf.py:194-259, 279+` — one `PdfImage` per photo, no cap
- `app/routers/pricing.py:539-543` — same load-all-then-slice for quotations

**Evidence.** `load_record_views` issues three unfiltered `SELECT`s, materialises every
row (with `selectinload` of photos, participants, work items and item photos when
`include_evidence=True`), appends to a Python list, then `records.sort(...)` at line 492.
`/records` and `/reports` then discard everything outside a 10-row window
(`records.py:39`). `/reports/pdf` renders the entire set. The dedicated
`/maintenance/records`, `/installations/records` and `/general-maintenance/records` lists
do this correctly with SQL `LIMIT`/`OFFSET` — the unified views do not.

**Why it matters.** `run.py` and the documented service run a single uvicorn process. A
`GET /reports/pdf` with no filter, at a few thousand records with ~5 photos each, opens
and scales tens of thousands of images synchronously in the request thread. The process
blocks; every technician in the field gets timeouts. This needs no attacker — an
Administrator clicking "Export PDF" is enough. Any authenticated user can trigger it,
including a Customer (scoped to their Projects, so lower blast radius).

**Likelihood.** High as the dataset grows; near-certain at year-end reporting time.

**Affected users/data.** All users — this is a full service outage while it runs.

**Remediation.**
(a) Push pagination into SQL for `/records`, `/reports` and `/pricing/quotations` —
either three `LIMIT`-ed queries merged, or a `UNION ALL` over a normalised projection.
(b) Cap `/reports/pdf` at a bounded record count and refuse with a clear "narrow your
filters" message above it; or generate it as a background job with a download link.
(c) Cap embedded photos per record in the PDF.

**Effort:** Medium (a, c); Large (b as a background job).
**Migration/ops:** None.

**Verification test.** Seed 2,000 records; assert `/records?page=1` issues bounded queries
and returns under a threshold; assert `/reports/pdf` over the full set either completes
within a budget or returns a bounded-set error.

### TEST-01 — Alembic migrations are never executed by any test; the suite builds its schema with `create_all()`

**Severity:** High
**Confidence:** Confirmed
**Category:** Testing / migrations

**Affected files**

- `tests/conftest.py:68-74` — `Base.metadata.drop_all(...)` / `Base.metadata.create_all(...)`
- `README.md:278` — claims `test_database_migrations.py` exists
- `scripts/Deploy-Release.ps1:191` — `alembic upgrade head` runs against production

**Evidence.** Every test runs against a schema generated directly from the ORM metadata.
`tests/test_database_migrations.py` **does not exist** — the directory contains 14 test
files and that is not among them. `README.md:270` claims 160 tests; the suite reports
**170**.

The chain was verified statically: it is linear with a single head
(`bc0a78bbcdf8 → d84b2a9f4c10 → f12c7b39a640 → a9d4e5f6c712 → b41d9c7e2a53 →
c62e8a14d907 → d74f0b2c91e3 → e85a1c3d72f4`), no branches, every `upgrade()` has a
matching `downgrade()`, and all **45** model tables are covered by `create_table` calls
across the migrations. That is reassuring but it is not the same as executing them.

**Why it matters.** The one code path that touches production data destructively is the
one path with zero automated coverage. Any drift between `models.py` and the migration
chain — a column added to a model without a revision, a type mismatch, a missing index —
is invisible until `alembic upgrade head` runs on the customer's server during a
maintenance window, with the service already stopped.

**Likelihood.** Medium now (chain currently looks consistent), rising with every future
schema change.

**Affected users/data.** Entire production database during upgrade.

**Remediation.**
(a) Add a session-scoped fixture (or a separate test database) that runs
`alembic upgrade head` instead of `create_all()`.
(b) Add a drift test using `alembic.autogenerate.compare_metadata` asserting the diff
against `Base.metadata` is empty.
(c) Add a `upgrade head → downgrade base → upgrade head` round-trip test.
(d) Reinstate `test_database_migrations.py` or correct `README.md:278`.

**Effort:** Medium.
**Migration/ops:** None.

**Verification test.** The drift test itself is the verification:

### SEC-03 — `backup_directory` and `pg_dump_executable` reach a SYSTEM scheduled-task command line without quote validation

**Severity:** Medium
**Confidence:** Confirmed
**Category:** Injection

**Affected files**

- `app/deployment_config.py:269-274` — validation: non-empty, no `\r\n`,
  `PureWindowsPath(value).is_absolute()`
- `app/deployment_config.py:598-599` — `$backupDirectory = {_ps(...)}`
- `app/deployment_config.py:617-625` — string-concatenated into `$taskCommand`, passed to
  `schtasks /TR ... /RU SYSTEM /RL HIGHEST`

**Evidence.** `_ps()` (line 280) escapes `'` → `''`, which is correct for a PowerShell
single-quoted literal, but performs no other filtering. A double quote survives
validation:

```
'C:\x" & calc.exe & "'  ->  PureWindowsPath(...).is_absolute() == True
```

That value becomes a valid PowerShell literal, then is concatenated into `$taskCommand`
between double quotes at line 620 and handed to `schtasks /TR`, whose command line is
parsed by the shell at execution time — as `SYSTEM`.

**Why it matters.** It converts a stored Settings value into arbitrary code in a
`SYSTEM`-privileged scheduled task. It does not cross a meaningful privilege boundary as
designed (only Administrators reach `/settings`, and the script must be manually
downloaded and run elevated), which is why this is Medium and not High. But it defeats the
stated invariant that the web process only stores validated, secret-free values, and it
becomes a real escalation if an Administrator account is ever compromised or if a
lower-privileged operator is given the Administrator role.

**Likelihood.** Low as an attack; the validation gap itself is certain.

**Remediation.** Restrict both path fields to a conservative character class (letters,
digits, space, `\ / : . _ -`) and reject `"`, backtick, `$`, `&`, `|`, `<`, `>`, `%`.
Better still, register the task with `Register-ScheduledTask` and a
`New-ScheduledTaskAction -Argument` array rather than building a `schtasks /TR` string.

**Effort:** Small.
**Migration/ops:** None.

**Verification test.** `validate_profile` must reject `C:\x" & whoami & "` for both fields.

### REL-02 — Uploads are read fully into memory with no aggregate request cap

**Severity:** Medium
**Confidence:** High
**Category:** Reliability / DoS

### DEP-01 — Documented Windows service binding contradicts the loopback + port-proxy design

**Severity:** Medium
**Confidence:** Confirmed
**Category:** Deployment / network exposure

**Affected files:** `docs/PRODUCTION_UPDATES.md:28-31`; `app/deployment_config.py:319-320`,
`:483-494`

**Evidence.** The runbook specifies the service arguments as
`-m uvicorn app.main:app --host 0.0.0.0 --port 8993`. Explicit uvicorn CLI flags take
precedence over `.env`, so `APP_HOST` is ignored. Meanwhile the apply script writes
`APP_HOST=127.0.0.1` and builds the entire exposure model — `netsh interface portproxy`
listeners plus firewall rules scoped to
`-LocalAddress $publicIp -RemoteAddress $allowedRemoteIps` — on the premise that the
application itself listens only on loopback.

**Why it matters.** As documented, the app listens on every interface at `:8993`. The
carefully scoped public firewall rule covers `$publicPort`, not `$internalPort`, so the IP
allow-list can be bypassed by connecting to `:8993` directly. The saving grace is that
Windows Server's default inbound policy is block and the apply script creates no rule for
the internal port — so in practice the port is unreachable. That is why this is Medium:
correct today by accident of the default firewall posture, wrong by design, and it fails
open the moment anyone adds a broad inbound rule or runs on a host with a relaxed profile.

**Likelihood.** Medium.

**Remediation.** Change the documented service arguments to `--host 127.0.0.1 --port 8993`,
or drop the explicit flags and let `run.py`/`.env` govern. Optionally have the apply script
assert nothing is listening on `0.0.0.0:$internalPort`.

**Effort:** Small.
**Migration/ops:** Ops change (service reconfiguration).

**Verification test.** After apply, `Get-NetTCPConnection -LocalPort 8993 -State Listen`
shows only `127.0.0.1`.

and `New-ReleasePackage.ps1` does not copy `data/`. Purely local hygiene.

**Remediation.** Delete after confirming nothing is needed. If any contains real data,
treat it as a copy of production data and dispose of it accordingly.

**Effort:** Small.
**Migration/ops:** None.

### Informational

- **INF-01 — Session revocation is limited by design.** Cookie-based sessions with
  `auth_version` (`deps.py:38-40`) mean password reset and deactivation end sessions on the
  next request, but there is no "log out everywhere". Role and `pricing_access` changes
  take effect immediately because `get_current_user` re-reads the row each request —
  verified against `deps.py:32-43`. Documented at `README.md:315`. No defect.
- **INF-02 — No combined administration audit log.** Record edits (`record_revisions`) and
  Deployment Settings (`deployment_settings_audit`) are audited; Project, Site, service,
  device, user and Pricing changes are not. Documented at `README.md:319-321`. Worth
  planning before any compliance requirement lands.
- **INF-03 — Migration locking is acceptable at current scale.** Every
  `ADD COLUMN ... NOT NULL DEFAULT` uses the PG 11+ fast path; `CREATE INDEX` (not
  `CONCURRENTLY`) and `ADD CHECK CONSTRAINT` take blocking locks with full scans, but the
  service is stopped during deployment anyway. Revisit if tables reach millions of rows.
- **INF-04 — Search uses unindexed `ILIKE '%term%'`.** Leading-wildcard patterns cannot use
  B-tree indexes, so search is a sequential scan across many columns and correlated
  subqueries. Fine at hundreds/low thousands of rows; add `pg_trgm` GIN indexes if search
  slows.
- **INF-05 — Quotation identifiers are visible to all record submitters.**
  `quotation_choices` (`quotation_references.py:10-19`) returns every quotation, and the
  entry forms render number + project name into a `<datalist>`. This is the documented
  intent ("All submitters may select the ID without gaining Pricing access") and no price
  is exposed. Note it also renders unboundedly — relevant to PERF-01.
- **INF-06 — Single-server architecture limits.** Cookie sessions and local-disk uploads
  mean horizontal scaling needs shared storage; documented at `README.md:309`. Accepted.

## 5. Database and migration assessment

### Schema integrity — strong

- 45 model tables; all 45 created across the migration chain. No orphan tables, no missing
  tables.
- Foreign keys are deliberate and correct: `RESTRICT` on catalog references from history
  (sites, service types, users, devices, installed devices), `CASCADE` on owned children
  (participants, photos, work items, quotation lines/charges), `SET NULL` on
  `quotation_id` in all three record tables — which is exactly right, since
  `quotation_number` is separately snapshotted so deleting a quotation cannot erase the
  historical identifier.
- `CheckConstraint`s enforce non-empty names/notes, non-negative money, positive
  quantities, valid percentage ranges, `valid_until >= quotation_date`, port ranges,
  singleton `id = 1` on both settings tables, and the charge-type enum.
- Unique constraints cover every record number, usernames, service names,
  `(site, customer)`, `(device name, model)`, `(quotation, position)`,
  `(quotation, charge_type)`, and every `storage_key`.
- Snapshot columns are applied consistently across `maintenance_records`,
  `installation_records`, `general_maintenance_records`, all `*_record_items`,
  `installed_devices`, and quotation lines. The invariant holds.

### Migration chain — healthy

Linear, single head, no branches:

```
bc0a78bbcdf8 → d84b2a9f4c10 → f12c7b39a640 → a9d4e5f6c712
             → b41d9c7e2a53 → c62e8a14d907 → d74f0b2c91e3 → e85a1c3d72f4
```

Every revision has a real `downgrade()` that reverses its `upgrade()` in correct
dependency order. Data migrations are conservative — `d84b2a9f4c10:50-66` links historical
participant name snapshots to user accounts only when exactly one active Technical account
matches, leaving ambiguous rows `NULL` rather than guessing. That is the right call.

### Upgrade safety — good

Additive throughout. New non-nullable columns use `server_default` then drop it
(`d74f0b2c91e3:41-46`, `e85a1c3d72f4:98-105`), which is the correct pattern for existing
rows. Nothing is dropped in the same revision that stops using it.

### Rollback compatibility — adequate, with the documented caveat

`Rollback-Release.ps1` reverts code only. Because migrations are additive, an older
application generally runs against the newer schema. The risk is real but correctly
disclosed (`docs/PRODUCTION_UPDATES.md:113-115`, and the script's own `Write-Warning`).

### Production-data risks

- **TEST-01 is the material one** — the chain is never executed by any test.
- REL-01 affects three counter tables plus quotations.
- No index gap identified; every filtered column is indexed. Search performance (INF-04)
  is a scan issue, not a missing-index issue.
- Locking is a non-issue at current scale with the service stopped during deploys
  (INF-03).

## 6. Backup and recovery assessment

### What is protected

- PostgreSQL, via the scheduled task: custom-format `pg_dump`, configurable 1-365 day
  interval, 1-365 dump retention, 02:00 SYSTEM task. Credentials are read from `.env` at
  runtime and never embedded — genuinely well done.
- PostgreSQL, `.env` and the **full uploads directory** at release time, via
  `Deploy-Release.ps1:155-181`, taken with the service stopped so the DB/photo pair is
  consistent. Also good.
- The apply script snapshots `.env` and prior network state before changing anything.

### What is not protected

> **Post-remediation:** the first bullet is now closed. Each scheduled run writes a dated
> `uploads-<timestamp>` snapshot beside its matching dump, driven by enumerating the live
> upload directory so deleted photos do not reappear, using NTFS hardlinks for unchanged
> immutable files with a per-file copy fallback, pruned by its own retention count. The
> remaining three bullets are still open.

- ~~**Uploaded photos, between releases** (BAK-01) — the largest gap.~~ **Closed.**
- **Backup integrity** — no checksum, no test restore, no `pg_restore --list` validation.
  Staleness and failure are now surfaced (BAK-02), but **no restore has been rehearsed**.
- **Backup confidentiality** — dumps and `.env` copies land in filesystem paths with no
  ACL hardening (SEC-02, still open). A `.dump` contains every bcrypt hash and all customer
  data.
- **Off-site copies** — everything stays on the same host. A single-server failure,
  ransomware event, or theft loses primary and backup together.

### Restore readiness — partial

`docs/PRODUCTION_UPDATES.md:117-136` gives a correct `pg_restore` command into a
*recovery* database and correctly instructs restoring uploads from the matching backup.
Keeping restore manual and deliberate is the right choice. But there is no runbook for
restoring from a *scheduled* dump (which has no paired uploads at all), no RTO estimate,
and no rehearsal.

### Retention and storage risks

- Scheduled dumps: bounded by `backup_retention_count`. OK.
- Deployment backups: **unbounded** (OPS-01), each including a full upload copy.
- Old `releases\` directories: unbounded.
- `data/deployment-backups/env-before-version-N.txt`: unbounded.
- No free-space precondition check anywhere.

### Recommended recovery testing

1. Quarterly: restore the latest scheduled dump into a scratch database; assert row counts
   against production and that `alembic current` matches head.
2. Quarterly: full pair restore (deployment dump + uploads) into a scratch environment;
   assert **every** `storage_key` across all four photo tables resolves to a file on disk.
3. Annually: timed bare-metal rebuild to establish a real RTO.
4. Continuously: alert when `last_success_utc` exceeds the configured interval (BAK-02).

### RPO/RTO as it stands

*At review time:* database RPO = the configured interval (default 1 day). **Photo RPO = time
since the last deployment** — potentially months. RTO unmeasured.

*Post-remediation:* photo RPO now equals the database RPO, since both are captured by the
same scheduled run in a fixed dump-then-snapshot order. RTO remains **unmeasured** until a
restore drill is performed.

## 9. Final verdict (as at review time, 2026-07-30 — superseded by 9.1)

**Ready only after the listed blockers.**

The application layer is production-grade. The review probed for the things that usually
break systems like this — privilege escalation, IDOR, CSRF gaps, injection, path
traversal, template escaping, customer data bleed — and found none. The authorization
model does what the documentation claims, verified across all 94 routes and five
identities rather than taken on trust. That is a materially better result than most
systems of this size produce.

The blockers are not application-logic defects. They are:

- **A deployment posture that undoes the application's security** (SEC-01). Careful bcrypt
  hashing, session invalidation and CSRF tokens do not survive an unencrypted public
  listener with no login throttle. This is the one finding that could produce full
  compromise, and it is a configuration and infrastructure fix, not a code rewrite.
- **A confirmed concurrency defect that destroys field evidence** (REL-01). It was
  reproduced. It is a one-line-per-call-site fix and it should not ship as-is.
- **A backup story with a hole exactly where the product's value lives** (BAK-01, BAK-02).
  A database-only backup for a photo-evidence portal, with no way to notice when it stops
  running, is the difference between an incident and a business loss.
- **The absence of any test over the one destructive production operation** (TEST-01),
  compounded by a README that claims such a test exists.
- **Unbounded work on a single worker** (PERF-01), where an ordinary Administrator action
  can take the system down for the field team.

None of these require architectural change. Items 1-6 are realistically one focused
sprint, and four of them are small. The verdict should become **Ready for production**
once they are done and one end-to-end restore drill has actually been performed — not
merely documented.

One structural note worth acting on before the codebase grows: the three ~1,000-line
submit/edit handlers are near-duplicates, and INT-02 is the visible symptom — a validation
rule correctly applied in two places and silently missing from the other three. That
pattern will keep producing findings. Consolidating it is the single highest-leverage
maintainability investment available.

## 9.1 Current verdict — post-remediation

**Ready for production, subject to one operational step the code cannot perform.**

All six blockers identified in section 9 are closed. The two that mattered most were closed
with evidence rather than assertion: the record-number race was reproduced before the fix
and is now covered by a two-thread, two-session concurrency test; and the pagination rewrite
— which touched the code path enforcing Customer Project isolation — was re-probed
end-to-end across multiple pages with interleaved records from two Projects, in HTML and in
extracted PDF text, showing zero leakage and zero over-filtering.

Isolation is in fact now **structurally stronger** than at review time. Scoping lives in one
place, `record_views.py`'s shared condition builder, and is applied to the count query, the
page-ID selection *and* the hydration query, so hydration re-applies it on top of
`id.in_(page_ids)`. At review time the same rule was duplicated across three call sites.

Two qualifications on the verdict:

1. **The restore drill has not been run.** Backups are now complete and their failure is
   visible, but nothing has yet proven a restore produces a working system with resolvable
   photos. This is the one remaining item I would not go live without.
2. **HTTP is an accepted risk, not a closed finding.** The operator has decided against TLS.
   Throttling and the mandatory remote-network allow-list reduce the brute-force and
   exposure surface; they do nothing about traffic interception. SEC-02 — plaintext
   `SECRET_KEY` copies on disk — compounds this and is the highest-value remaining fix,
   because a leaked signing key plus an unencrypted transport are worse together than
   either alone.

What remains open is next-release work rather than go-live work: SEC-02, OPS-01, REL-02 and
DEP-02 at Medium, then the Lows. None of them blocks deployment.
